# Flame Chick Production Database — Security, Idempotency & Reliability Controls V1

**Status:** Required design contract before test migrations  
**Date:** 2026-11-20  
**Branch:** work/production-source-audit  
**Applies to:** Website, POS, Admin, Rider, Edge Functions, PostgreSQL and Storage  
**Production state:** Documentation only; no Production DDL or settings are changed by this document.

## 1. Non-negotiable boundaries

1. Production remains read-only until a specific reviewed migration batch and rollout are explicitly approved.
2. Never put Supabase service-role/secret keys in a browser, repository, source map, build artifact, log or support response.
3. Every exposed public table has RLS enabled and explicit least-privilege grants. An absent policy means deny.
4. The database, not the UI, is the final authority for identity, role, branch, prices, availability, delivery fees, order state and idempotency.
5. Multi-row business operations use one database transaction. Do not split an order, assignment, payment, publish or audit write across independent REST requests.
6. Business history is not physically deleted through normal apps, including Admin/Owner. Use state changes, archival of editable catalog records and append-only correction/audit events.
7. GST/tax and ingredient inventory remain out of V1 as already decided.
8. Preserve the four existing domain Edge Functions. Frequent POS/Rider reads use RLS-protected Data API where safe; do not create a new Function for each CRUD operation or poll Functions every 15 seconds.

## 2. Idempotency is required on all retryable writes

Idempotency is not a rate limit. It protects against duplicate business records when a browser retries after a timeout, a button is double-clicked, the network drops after database commit, a POS device reconnects, or a provider/webhook resends an event.

### 2.1 Order creation — Website and POS

Both Website and POS must use a stable idempotency key, but their quota policies differ:

| Source | Idempotency | Customer website phone quota |
|---|---|---|
| Customer website (source=website) | Required | 3 per rolling minute, 3 per rolling 10 minutes, 15 per rolling hour per normalized phone |
| POS (source=pos), including POS delivery | Required | Exempt |
| Authenticated staff-entered phone/WhatsApp/manual/third-party | Required where submitted through the shared order command | Exempt |

The customer website quota is enforced only when the server has positively classified the request as source=website. Do not derive quota eligibility from a customer-controlled field that can be changed by an anonymous caller; the Edge Function must strictly allowlist the public source route, while non-website sources require verified staff Auth and role. POS must never call or consume the website quota, even though POS delivery currently uses the same Order API.

### 2.2 Order idempotency fields and unique scope

The orders table carries:
- idempotency_key text NOT NULL
- request_fingerprint text NOT NULL
- source text NOT NULL
- restaurant_id and branch_id
- created_at generated by the database

Enforce a unique constraint on (restaurant_id, branch_id, source, idempotency_key), or a deliberately equivalent key scope verified against the current apps. The unique constraint is the final concurrency backstop; a client-side key check is never sufficient.

The Website currently stores its pending request payload and generated key in sessionStorage. Keep that exact pending key/payload until the server confirms success or the user deliberately edits/discards the request. A 429 or transient error must keep both the cart and pending key.

The POS currently derives its idempotency key from its stable local order ID (for example, flame-chick-pos-<localOrderId>). Preserve the same key for every retry of that local order, including after reload/reconnect. Do not generate a fresh order ID/key just because a request timed out.

### 2.3 Canonical request fingerprint

- Build the fingerprint on the trusted server from a validated, normalized, allowlisted representation of all business-significant input: source, tenant/branch scope, customer fields used for the order, fulfillment, selected area choice, address/instructions where relevant, catalog publication/version, product/variant/deal choices, quantities, modifiers, notes, payment method and the authenticated actor for staff sources.
- Exclude transport noise (header order, JSON key order, retry count, IP headers, client timestamps) and server-generated fields (order number, created_at, computed price, computed fee, status, verified actor fields supplied by server).
- Do not trust a browser-supplied fingerprint. Do not hash raw JSON text whose serialization can differ for semantically identical requests.
- Store a cryptographic request fingerprint (for example SHA-256 of canonical JSON). This is an idempotency comparison value, not an identity secret; the phone limiter itself uses HMAC, not a plain phone hash.

### 2.4 Transaction sequence and concurrent retries

The service-only order RPC must perform this sequence inside one transaction:

1. Validate that the caller path is authorized for its source. Website is the public guest route; POS and other staff sources require a verified Auth user and current role/branch.
2. Resolve the restaurant/branch on the server; never trust caller-supplied tenant IDs as authority.
3. Acquire a transaction-scoped advisory lock derived from the idempotency scope/key. Use a fixed lock ordering for every command to avoid deadlocks.
4. Look up (restaurant, branch, source, idempotency_key).
5. If found with the same canonical fingerprint, return the original order identity/number and a safe current summary. Do not create order items, status history, delivery task, payment, notification or rate event again.
6. If found with a different fingerprint, return HTTP 409 IDEMPOTENCY_KEY_REUSED. Never mutate the original order to match the new request.
7. If not found and source is website only, take a second transaction lock keyed by server-generated normalized-phone HMAC; evaluate all three website rolling windows before creation. POS/staff paths skip this check.
8. Validate catalog publication and current product/deal/modifier eligibility; compute all money and delivery fee server-side.
9. Insert order and all snapshots, initial order event, payment intent/record if appropriate, delivery task if delivery and one website rate event if website. Commit the entire operation together.
10. Only report successful creation after the database transaction commits.

If two copies of the same request arrive concurrently, the lock plus unique constraint ensures one order. The losing request re-reads the committed row and returns it only when fingerprint matches; otherwise it returns 409. Test this with parallel requests, not just sequential tests.

### 2.5 Ambiguous network outcome

A timeout does not mean the database rolled back. The client must:
- Keep the original idempotency key and payload.
- Retry the exact same request using the same key, or query a narrow authenticated result endpoint by the key/scope if supported.
- Never create a replacement key until the server has established that the old request did not commit and the user has intentionally changed the order.
- Keep the local POS queue item until the server returns a confirmed order ID/order number.
- Show “checking order status” rather than “order failed” when the transport outcome is ambiguous.

### 2.6 Other commands and side effects

Use idempotency/deduplication on retryable writes beyond order creation:

- Order status changes, reject/cancel actions: require a request/command ID; store it uniquely with the status event, and make the same retry return the prior result without a second event.
- Delivery accept/decline, assignment/reassignment, pickup, delivered, failed, return report and physical-return confirmation: require command ID or a natural unique transition key. Enforce unique command/event IDs inside the same transaction as the state transition.
- Staff invite/role changes: persist the invitation/role audit event and action key. Do not create duplicate invitations or role history on retries.
- Catalog draft save/publish/rollback: use expected draft revision and command ID. A stale revision returns 409 instead of overwriting changes.
- Payment capture/record/refund/webhook when later implemented: require payment idempotency key and unique provider event/reference constraints. Do not infer or add a refund gateway now.
- Push/email/SMS notification side effects: insert an outbox event in the business transaction with a unique event key. Delivery is at-least-once; consumers/provider adapters must deduplicate where possible. A failed push must never roll back a committed order or delivery state.

Avoid introducing a generic high-volume idempotency table unless an actual API requires it. Prefer unique constraints on the canonical business record/event table; use a narrowly scoped private command receipt table only if a reliable replay response cannot be reconstructed from the business event.

## 3. Customer Website order quota — only this source

Owner-approved limits, all simultaneous, rolling and evaluated using database time:

| Window | Maximum committed website orders per normalized phone |
|---|---:|
| 1 minute | 3 |
| 10 minutes | 3 |
| 1 hour | 15 |

- This is website only. POS, including POS delivery, and authenticated staff channels are exempt. Keep POS order idempotency and normal security validation; do not call the quota path for POS.
- Count only a newly committed website order. Invalid payload, failed price/area validation or rolled-back transaction consumes no slot. A later restaurant rejection/cancellation does not refund a slot.
- Exact idempotent replay returns the existing order and does not consume another slot.
- Use server-normalized phone plus HMAC-SHA-256 from an Edge Function secret. Never store raw phone or plain unsalted phone hash in the private event table. Key rotation keeps current and previous HMAC versions overlapping for at least the one-hour longest window.
- Store one append-only private rate event per committed website order, uniquely linked to the order; retain 48 hours with bounded cleanup.
- On quota denial return 429 RATE_LIMITED and Retry-After; leave the website cart and pending idempotency key intact.
- Phone entry is not OTP verification. Describe this accurately as a limit per normalized number supplied, not as a verified per-human limit.
- A 429 Edge Function response still consumes an Edge invocation. The quota protects committed order creation and database work, not the monthly invocation allowance from a volumetric flood.

The Demo reference limiter is not production-ready: it records attempt events before order creation, uses plain SHA-256 for phone, has different thresholds and a separate preflight RPC. Replace it with the website-only atomic logic above; POS bypasses the quota branch.

## 4. Authentication, RLS and database grants

### 4.1 Browser credentials

- Browser apps may contain only the project's publishable/anon key and a user's short-lived access token.
- Service-role/secret keys remain exclusively in Edge Function environment secrets.
- Never treat CORS, obscured URLs, hidden buttons, static JS constants or a frontend route guard as authorization.

### 4.2 RLS for all public application tables

For each public table:
- Enable RLS explicitly; test policies with anon, ordinary authenticated user, each staff role, Rider, Manager and service-only caller.
- Default deny. Add SELECT/INSERT/UPDATE/DELETE policies only for a real application requirement.
- Prefer client SELECT-only for direct operational reads and move critical mutations into narrow RPC/Edge commands.
- Enforce tenant and branch membership in every row predicate and every transactional command. Never accept a caller-supplied branch ID without checking it against the verified role.
- Rider tasks/offers/assignments must be constrained by auth.uid() and active rider profile, so one Rider cannot infer another Rider's offer or task.
- Manager is POS-only and cannot use Admin data APIs or menu/staff/settings/publish endpoints. Deny at server and database layer, not only UI.
- Cashier can reject only a newly received/unaccepted order with an audit reason, cannot delete, and cannot cancel accepted/in-progress orders unless separately approved.
- Cashier or Manager may confirm physical return only for an authorized return-pending task. Rider may report/choose return, but cannot confirm receipt.
- Admin/Owner have their documented business permissions, but no normal app role receives hard-delete access to orders, financial history or audit events.

### 4.3 SECURITY DEFINER and RPC rules

For every SECURITY DEFINER function:
- Set a fixed safe search_path (prefer empty path plus schema-qualified references).
- Own the function with a controlled non-login owner as appropriate; do not let browser roles own it.
- Revoke EXECUTE from PUBLIC, anon and authenticated by default.
- Grant EXECUTE explicitly to the smallest intended role. For service-only RPCs, explicitly grant service_role; Production default privileges revoked its implicit function/table/sequence privileges.
- Validate verified actor, role, branch, resource state and allowed transition inside the same transaction. Never trust payload actor_user_id/role/branch as proof.
- Do not use user-editable Auth metadata to authorize roles.
- Keep function parameters narrow and typed. Reject unknown action names, oversized payloads and unexpected fields.

A Supabase service_role request can bypass RLS; therefore service-only RPCs and Edge Functions must still perform explicit business authorization and branch validation.

### 4.4 Privilege verification

After every migration, inspect information_schema/catalog grants and policies. Test that anon/authenticated cannot:
- Read orders, customer PII, payment records, private limiter/outbox data or another Rider's work.
- Execute order creation through a direct privileged RPC or mutate prices/fees/status.
- Update their own role, branch, ownership or audit actor.
- Delete orders, order items, status events, delivery events or audit rows.
Also verify the exact service-role command grants still work after default privilege hardening.

## 5. Data integrity and transaction rules

- Use UUID primary keys and composite tenant/branch foreign keys so an ID from one branch cannot be attached to another branch.
- Use ON DELETE RESTRICT for orders, order items, payment records, delivery tasks, rate events and audit history. Avoid cascading deletion of business history.
- Use NOT NULL, CHECK constraints, unique constraints, typed references and valid status sets for invariants that must survive API bugs.
- Money uses numeric(12,2) and server/database calculations; no browser-supplied subtotal, total, item price, modifier price or delivery fee is trusted.
- Snapshot product/deal/variant/modifier labels, unit prices, quantities, delivery area/fee, fulfillment/address and catalog publication on the order. Later menu/fee edits do not rewrite historical orders.
- Use database-generated timestamps (timestamptz) for created/updated/state events. Do not trust browser timestamps for order, delivery, acceptance or audit chronology.
- Every status change is a controlled transition with a row lock or equivalent concurrency-safe compare-and-set. Insert its append-only history event in the same transaction.
- A delivery offer accept checks database time at the instant of the locked transition; the 60-second client countdown is presentation only.
- Atomic multi-row commands either fully commit or fully roll back. Never leave an order without required items, a delivery task without its order, a confirmed return without its event, or a published pointer without the immutable publication.
- Make audit/history tables append-only through grants and, where needed, defensive triggers. Do not create generic mutable audit blobs that can be rewritten by normal roles.

## 6. Reliable retries, outbox and offline POS

### 6.1 Retry policy

- Retry only transient transport failures, 408, 429 (respect Retry-After) and selected 5xx errors using bounded exponential backoff with jitter.
- Do not automatically retry validation, permission, not-found or idempotency-conflict 4xx responses.
- Refresh expired Auth once where appropriate; do not create unbounded refresh loops.
- Every retry of the same business action uses the same idempotency/command ID.
- Bound payload size, database work, response size, retries and concurrency. Use request timeouts and abort signals where client/server runtime supports them.
- Treat database/limiter unavailable as fail closed for the protected website order path: no bypass and no silent order creation with missing rate check. POS must remain exempt from website quota but still fail safely on required database/price/idempotency dependencies.

### 6.2 POS offline queue

- Keep a stable localOrderId from initial cashier action through retries/restart.
- Keep the same server idempotency key for all submissions of that local order.
- Do not delete local queue until server confirms a matching order ID/order number.
- If server commit outcome is unknown, retry/query by the same key; never create a new server order blindly.
- Stale catalog/price/availability requires explicit Cashier/Manager confirmation under the approved policy; no silent reprice.
- Keep last-known-good menu cache until a new publication is fully downloaded, validated, checksummed and staged; switch atomically only after success.
- If the database is unavailable and price/fee cannot be validated, do not claim cloud submission succeeded. Retain local receipt/queue and surface pending state clearly.

### 6.3 Transactional outbox

Use the private outbox only for side effects that must follow a committed business event (rider push, customer notification, dispatch notification):
- Insert outbox row in the same transaction as the order/delivery transition.
- Unique key includes event type + business event identity + recipient/channel so retries do not enqueue duplicates.
- Track bounded status/attempt count/next_attempt_at/last_safe_error and lease/claim metadata. Do not store secrets or full request payload.
- Send after commit, with bounded timeout/backoff. A failed push is visible for retry and does not roll back a successful order.
- No continuous worker/new Edge Function is required in V1; opportunistic bounded processing can be triggered by an existing operational request if safe. Correctness must never depend on the push succeeding.

## 7. Auditability and privacy

- Record actor from verified Auth/JWT (or explicit system actor), role snapshot, branch, action, resource ID, before/after status where relevant, server timestamp, reason code/note and request/command ID.
- Rejection, cancellation, failed delivery, return report and physical-return confirmation must state who did what and when. Keep the original event even after later correction.
- Do not persist raw IP in audit/rate tables unless an explicit security/legal policy requires it and retention is approved. For optional IP abuse signals, use a trusted ingress header only after spoof tests and HMAC the value server-side.
- Redact tokens, publishable/service secret values, payment credentials and customer PII from logs. Avoid logging whole request bodies. Use safe error codes and a correlation ID.
- Minimize PII in API projections. Rider receives only the customer/contact/address/items needed for their own current assignment; POS/Admin access remains role/branch-scoped.
- Define and document retention/deletion rules for customer contact details, operational events and backups before launch; retain legal/financial order snapshots according to business obligations rather than opportunistically deleting them.

## 8. Performance and Supabase Free-plan discipline

- Preserve four domain Edge Functions (catalog, order, delivery, staff-admin). No per-CRUD Functions, no Function chaining.
- POS 15-second polling and Rider read recovery use direct RLS-protected Data API queries where safe; no Function invocation per poll.
- Realtime only for narrow POS/Rider operations; Rider filters by rider user ID, POS filters by branch. Order History/reports use paginated normal reads/manual refresh.
- Paginate order history and Admin dashboard reads; never load an arbitrary 1,000-row order history at startup. Select only needed columns and use server-side filters/cursors.
- Add indexes for observed filters/joins/order clauses and RLS predicates, then validate with EXPLAIN (ANALYZE, BUFFERS) on representative data. Avoid redundant indexes because each adds write/storage cost.
- Cache immutable catalog by publication version/checksum. Compress WebP/AVIF and avoid duplicate media.
- Retain manual invocation warning thresholds: 50% / 250k investigate, 70% / 350k optimize, 85% / 425k degradation plan, 95% / 475k suspend nonessential function calls while protecting essential operations. These are operational checks, not platform alerts.
- Keep an eye on DB size, Storage, egress, Realtime messages/connections and organization-level Edge invocation usage. Recheck official limits at implementation/cutover.

## 9. Backups, recovery and migration hygiene

- Free-plan dashboard backups are not a substitute for a separately verified restore process. Database and Storage/media require separate backup coverage.
- Maintain encrypted off-project backups with access controls and a written retention schedule. Do not commit dumps, customer PII or secrets to the application repository.
- Verify backup completeness, checksum and encryption. Perform periodic restore tests into an isolated environment; a backup not restore-tested is not a proven recovery mechanism.
- Before each production migration: capture a fresh restorable backup, record current migration state, review generated SQL, run on isolated test database, run smoke/security/negative/concurrency tests, estimate table locks/downtime and prepare a forward-fix or rollback plan.
- Prefer additive expand/migrate/contract changes: add compatible columns/tables, deploy a versioned API adapter, backfill/validate, switch clients, then remove obsolete fields only after confirmed no old client uses them.
- Migrations must be sequential, deterministic, idempotent where feasible, checked into Git and recorded in Supabase migration history. Never manually change Production schema outside the reviewed migration process.
- Never assume a preview/test project exists or that Free permits additional active projects; verify available project slots or use local Supabase for isolated tests.

## 10. Required verification matrix before enabling writes

### Idempotency and transaction integrity
- Same Website key + same payload sequentially and concurrently returns one order.
- Same POS key + same payload sequentially and concurrently returns one order; POS still succeeds when website quota would deny the phone.
- Same key + changed canonical payload returns 409 and never modifies the original.
- Timeout immediately after commit, followed by retry, returns the original order.
- Failure at every intermediate insert rolls back order, items, task, status event, outbox and website quota event.
- Retry of status/dispatch/Rider/return/publish/staff command does not duplicate its append-only event or side effect.

### Website quota scope and behavior
- Website fourth order in rolling minute and 10-minute window is rejected; sixteenth within one hour is rejected.
- POS website-identical phone is not blocked by website counters, including POS delivery.
- Staff-authenticated sources are not blocked by website counters.
- Invalid/rolled-back website requests do not consume quota; restaurant rejection after commit does not refund the slot.
- Different phone subject has an independent quota; format variants normalize consistently; exact retry consumes no second slot.
- HMAC key rotation across one-hour overlap does not reset live quota.
- 429 includes bounded Retry-After, leaves cart/key intact, and is counted in Edge Function invocation metrics.

### Authorization, RLS and security
- Test anon, ordinary user, each staff role, Rider and Manager against every exposed table/RPC.
- Manager cannot call Admin endpoints directly or access menu/staff/fees/settings/publish commands.
- Rider cannot read other Riders' offers, task IDs, addresses or contact details, even by guessing UUIDs.
- Cashier cannot delete, cannot cancel accepted/in-progress orders, and can only reject newly received/unaccepted orders with a mandatory audit reason.
- Rider cannot confirm physical return; Cashier/Manager only confirm a return-pending task.
- Direct REST writes to order/status/price/fee/role/audit/private tables are denied unless explicitly required.
- Revoke PUBLIC/anon/authenticated EXECUTE on privileged functions and verify service_role grants explicitly after default privilege hardening.
- Cross-tenant/branch FK, forged branch/actor/role, malformed payload, oversized JSON, SQL injection strings and replay tests fail safely.

### Recovery and performance
- Restore latest encrypted database and Storage backup into isolated target and compare row counts/checksums/media reachability.
- Simulate network loss, browser reload, offline POS restart, missing Realtime, expired session and transient 5xx; no duplicate order and no silent loss.
- Verify query plans and pagination with expected operational volumes; monitor Edge invocation, DB size, egress and Realtime usage.

## 11. Implementation sequence

1. Finish source/schema field and status mapping using source-schema-consistency-audit-v1.md; maintain compatibility adapters for old browser clients.
2. Finalize table definitions and exact unique/foreign-key/check constraints, including universal order idempotency and website-only quota event.
3. Finalize RLS/grants and SECURITY DEFINER inventory. Produce allow/deny matrix per table and function.
4. Author isolated migration SQL only after schema review; run local/test migrations plus generated PostgREST API contract tests.
5. Implement Edge Function HMAC only for website submissions and atomic website quota within the central order transaction; POS uses same idempotent order command with quota branch bypassed.
6. Implement command idempotency, transactional outbox and audit constraints for protected delivery/staff/catalog actions.
7. Update clients with versioned request/response DTOs and compatible rollout.
8. Verify restore and concurrency/security tests. Obtain explicit per-batch approval before any Production migration or deployment.
