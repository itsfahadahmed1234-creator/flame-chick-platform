# Flame Chick Production — DDL Specification for Foundation Batches 1–3

**Status:** Pre-SQL specification; not executable SQL and not approval to apply migrations  
**Date:** 2026-11-20  
**Branch:** work/production-source-audit  
**Target:** PostgreSQL 17 / Supabase  
**Prerequisite:** Read-only Batch 0 baseline verified.  
**Production boundary:** No DDL or settings changes authorized by this document.

## 1. Purpose and implementation gate

This specification defines the first foundation layer:
1. Private schema and privilege boundary.
2. Restaurant/branch tenant foundation.
3. Staff profiles, role assignments, role audit and recoverable invitation workflow records.

It intentionally does not create catalog, order, payment, delivery or drop-off pin tables yet.

Before any isolated migration is applied, verify the migration connection's effective database role is `postgres`. The Production catalog still has broad default ACL entries for objects created by internal `supabase_admin` in `public`. Never create Flame Chick application objects as `supabase_admin`. If ownership cannot be proved, stop.

No Production SQL is permitted without separate explicit approval.

## 2. Naming and shared conventions

- Use `public` only for intentional Data API-facing tables or narrow RPC wrappers.
- Use `app_private` for internal tables, helper functions, secrets metadata and internal event data. Do not add it to Supabase exposed schemas.
- All IDs are UUIDs generated by `gen_random_uuid()`.
- All business tables include `created_at timestamptz NOT NULL DEFAULT transaction_timestamp()`; mutable tables also have `updated_at` maintained by a trusted trigger.
- Money is `numeric(12,2)`; never use floating point.
- Time is stored as `timestamptz`; local schedule rules store IANA timezone separately.
- Every branch-scoped table has `restaurant_id` and `branch_id` and a composite FK to the matching branch.
- Prefer named CHECK/UNIQUE/FK constraints so errors and schema review are deterministic.
- Avoid ON DELETE CASCADE for business/financial/audit history. Use RESTRICT and explicit archival/retention.
- No business seed data or menu data in foundation migrations.
- Do not create Kitchen role or user account during migrations.

## 3. Batch 1 — private schema and privilege boundary

### 3.1 Schema

Create `app_private` owned by `postgres`, with no client role access:
- Revoke all schema privileges from PUBLIC, anon, authenticated and service_role.
- Do not grant USAGE to browser roles.
- Do not expose `app_private` in Supabase API exposed schemas. Supabase API exposed-schema configuration is a dashboard/API setting and is not readable from the SQL catalog queries available in this session; record a manual Dashboard check of **Project Settings → API → Exposed schemas** as a pre-migration and post-migration gate. User-confirmed exposed schemas are exactly `graph_ql` and `public`; `app_private` must not be present.
- Schema owner and object owner must be verified after migration.
- Explicitly enable RLS on every table created in `app_private` as defense in depth; do not assume the existing `ensure_rls` event trigger covers non-public schemas.
- Do not place client-facing RPCs in this schema; use narrow public wrappers only where required and grant exact EXECUTE to the intended caller.

### 3.2 Default privileges for postgres-created private objects

For objects created by `postgres`:
- PostgreSQL implicitly grants EXECUTE on new functions and USAGE on new types to `PUBLIC`. A schema-specific default-privilege REVOKE does **not** subtract those global implicit defaults; rollback-only probes against the connected PostgreSQL 17.12 database confirmed this.
- Do **not** change the global `postgres` function/type defaults as part of Batch 1. Such a global change affects every schema where `postgres` later creates functions or types, including areas outside Flame Chick's private application schema.
- In `app_private`, set schema-specific defaults:
  - Revoke default ALL on tables and sequences from PUBLIC, anon, authenticated and service_role.
  - Revoke default EXECUTE on functions from anon, authenticated and service_role.
  - Revoke default USAGE on types from anon, authenticated and service_role.
- Because the per-schema function/type revokes cannot subtract the implicit PUBLIC grant, every future private function migration must explicitly execute `REVOKE EXECUTE ON FUNCTION app_private.<exact_signature> FROM PUBLIC, anon, authenticated, service_role;` immediately after creation. Every future custom type must explicitly execute `REVOKE USAGE ON TYPE app_private.<type_name> FROM PUBLIC, anon, authenticated, service_role;` immediately after creation. Include a corresponding assertion in that migration.
- The schema itself remains inaccessible to PUBLIC, anon, authenticated and service_role. The API exposed-schema setting must also keep `app_private` out of PostgREST.
- Any intentionally callable public RPC must revoke PUBLIC/anon/authenticated and receive an explicit grant only to its exact intended caller; the rollback-only service_role wrapper probe passed.
- Explicitly grant only owner/maintenance permissions and exact function execution when a later migration requires it.
- Do not rely on these defaults to control objects created by `supabase_admin`; that internal-role default ACL remains a separate known limitation.

### 3.3 Public command wrapper policy

When later functions need Data API invocation:
- Keep wrapper in `public` with exact function signature and exact EXECUTE grants.
- Revoke EXECUTE from PUBLIC, anon and authenticated by default.
- Grant EXECUTE only to service_role for server-only order/staff/delivery commands, or to anon only for a deliberately public-safe read/write endpoint after threat review.
- Wrapper derives/validates all business inputs and calls schema-qualified internal functions.
- For SECURITY DEFINER: fixed/empty safe search_path, schema-qualified relation/function references, controlled postgres owner, no dynamic SQL from caller strings, explicit actor/role/branch validation, and exact EXECUTE ACL.
- Prefer SECURITY INVOKER unless a documented privilege boundary makes definer necessary.
- Never treat service_role as a human business actor.

### 3.4 Required Batch 1 verification

- Confirm schema owner = postgres.
- Confirm anon/authenticated/service_role have no USAGE on app_private.
- Confirm `app_private` is absent from Supabase API exposed schemas in Dashboard settings; SQL-only catalog inspection cannot prove this control. Confirm no app_private relation/function is discoverable through PostgREST using an authenticated negative API test once schema exists.
- Confirm no table/sequence/function/type default ACL grants unintended client roles; test actual effective privileges rather than inspecting ACL text alone.
- Confirm public wrappers have only intended EXECUTE grants.
- Confirm newly created objects are owned by postgres and RLS is enabled for any later exposed table.
- Confirm no app_private object appears in Realtime publication.

**Review status:** owner-approved business decisions recorded; exact DDL still requires source-contract reconciliation, isolated acceptance tests and separate migration approval. Batch 2 contains only `public.restaurants` and `public.branches`.

### 4.0A Owner-confirmed Batch 2 decisions (2026-11-20)

- `branch_code`: lower-case ASCII letters, digits, underscore and hyphen; 1–32 characters; unique per restaurant. Examples: `main`, `gulberg`, `dha-01`.
- `name`: customer-facing branch name; eligible for a future narrow public discovery projection.
- `address` and `phone`: operational/private fields; excluded from public discovery by default. No public disclosure is authorized.

- Branch resolution remains fail-closed: zero eligible branches blocks ordering; one eligible branch auto-resolves; multiple eligible branches require customer selection. Server revalidates the chosen branch for every relevant catalog/quote/order operation.
- These are design decisions only. They do not authorize SQL or a Production migration.

### 4.2 public.branches

Branches are operational locations under the single Flame Chick restaurant tenant.

Columns:
- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `restaurant_id uuid NOT NULL`
- `branch_code text NOT NULL` — stable unique code within the restaurant.
- `name text NOT NULL` — customer-facing branch label (1–120 trimmed characters).
- `address text NULL` — private operational address; not included in public discovery DTO by default.
- `phone text NULL` — private operational phone; not included in public discovery DTO by default.
- `is_active boolean NOT NULL DEFAULT true`
- `website_ordering_enabled boolean NOT NULL DEFAULT false`
- `website_delivery_enabled boolean NOT NULL DEFAULT false`
- `website_pickup_enabled boolean NOT NULL DEFAULT false`
- `created_at timestamptz NOT NULL DEFAULT transaction_timestamp()`
- `updated_at timestamptz NOT NULL DEFAULT transaction_timestamp()`

Constraints and write rules:
- FK `restaurant_id → restaurants(id)` ON DELETE RESTRICT.
- UNIQUE(`id, restaurant_id`) as the referenced composite tenant key.
- UNIQUE(`restaurant_id, branch_code`).
- Enforce canonical `branch_code` formatting in the database as well as at the command boundary (proposed lower-case ASCII key, 1–32 chars, limited to letters/numbers/underscore/hyphen). Never allow blank/whitespace-only codes.
- CHECK `name = btrim(name)` and character length is 1–120.
- CHECK each capability flag: delivery and pickup can be true only when `website_ordering_enabled` is true.
- All three website capability flags default false. No branch becomes website-orderable merely because the restaurant or branch row exists.
- Effective eligibility is derived server-side for the requested fulfilment mode: restaurant active AND branch active AND website ordering enabled AND the matching delivery/pickup capability enabled. A branch-level capability flag is only an enablement gate; delivery address must still pass that branch's delivery-area/Not-Listed rules later.
- No customer-facing direct SELECT. The future branch discovery command may return only the approved safe projection: opaque branch ID, customer-facing name and supported fulfilment modes. Do not return operational address/phone without an explicit public-field decision.
- `updated_at` must be updated by every trusted mutation command.

### 4.2A Application fulfilment contract (source-reviewed 2026-11-20)

Canonical values for future orders:
- `delivery`: Website and POS; delivery address/area and delivery-fee validation apply; delivery task may be created.
- `pickup`: Website and POS; this is the canonical stored value for the POS UI label Takeaway; no delivery address/area or rider task.
- `dine_in`: POS only; no rider task. Website active checkout currently exposes Delivery and Takeaway only.

Do not store a separate `takeaway` value. Keep customer/staff labels separate from canonical API/database values. The website's active checkout maps Delivery → `delivery` and Takeaway → `pickup`; its legacy `js/app.js` is not loaded and must not be treated as the active website contract. The POS contains Dine-in handlers despite its hidden UI controls; preserve Dine-in support in the future data/API model. Owner explicitly instructed not to fix the current POS UI mismatch now.

The authoritative source findings and sync requirements are in `docs/architecture/pos-fulfillment-and-offline-sync-contract-review.md`.

### 4.3 Tenant and branch FK rule for all future tables

For a branch-owned child:
- Store `restaurant_id NOT NULL` and `branch_id NOT NULL`.
- Add FK (`branch_id, restaurant_id`) → `branches(id, restaurant_id)` ON DELETE RESTRICT.
- Parent must have an exact UNIQUE key in the same column order for every composite reference, even where the first column is already the primary key.
- Every deeper relationship that could cross a tenant or branch must carry and constrain `restaurant_id` and `branch_id`, not rely only on a UUID FK.
- Tenant-wide entities carry `restaurant_id`; they do not get a fake branch ID.
- Nullable branch scope is reserved for explicitly restaurant-wide entities. NULL never means “all branches” for an operational permission.
- Do not use ON DELETE CASCADE for restaurant/branch business history. Deactivate/archive; historical FKs use RESTRICT.

### 4.4 RLS, grants and API boundary for Batch 2

Both tables live in the exposed `public` schema, so:
- Explicitly ENABLE ROW LEVEL SECURITY on each table in the migration.
- Explicitly REVOKE ALL table privileges from PUBLIC, anon, authenticated and service_role. Do not add client table policies or direct table grants in Batch 2.
- No direct grants to service_role yet. Later Edge Functions must use narrowly granted transactional RPCs or an explicitly reviewed server-side access path; possession of service_role is not a reason to expose all tenant rows.
- No public RPC, view or table projection is created in Batch 2. Add only a narrowly allowlisted branch discovery function in a later API-contract batch after exact inputs/outputs and caller grants are reviewed.
- RLS and SQL grants remain separate controls. RLS with no policies is deny-by-default for roles that do have table privileges; the absence of grants is an independent first gate.
- Table owner is postgres. Migration preflight must assert `current_user = 'postgres'` and `session_user = 'postgres'`.

### 4.5 Website branch resolution contract

For a server-verified Flame Chick tenant and requested fulfilment mode:
1. Compute eligible branches from live restaurant/branch state and the mode-specific capability flag.
2. Zero eligible branches: fail closed; do not silently choose an inactive branch or default to zero delivery fee.
3. Exactly one eligible branch: resolve it server-side automatically.
4. More than one: require explicit customer choice from the safe discovery projection.
5. On every catalog, quote and order command, revalidate the chosen branch ID against the same tenant, active state and requested mode. A browser branch ID is a selection hint, never authorization.
6. Delivery address eligibility/fee is a separate check against the selected branch's areas and explicit Not Listed fee. No GPS routing or distance-derived price is implied.

### 4.5 Batch 2 exact candidate DDL and validation status (2026-11-20)

Candidate SQL: `docs/drafts/batch2_restaurant_branch_foundation_candidate.sql`. This is a review draft, not an applied migration.

Only `public.restaurants` and `public.branches` are created. Both use UUID PKs, named constraints, RLS enabled, postgres ownership, and no direct privileges for PUBLIC/anon/authenticated/service_role. No policies, RPCs, views, functions, triggers, seed rows, Auth users or Realtime membership are created. The candidate requires postgres execution identity and checks Batch 1 app_private ownership plus absence of conflicting relation names.

Fail-closed defaults: restaurant and branch inactive; website ordering and both website capabilities disabled. Currency and timezone are required; trusted provisioning must validate supported ISO-4217 code and IANA timezone. Branch address/phone are private; branch name is customer-facing. Branch code is lowercase ASCII letters/digits with single underscore/hyphen separators, 1–32 chars, unique per restaurant. Composite unique (branch id, restaurant id) supports future tenant-safe FKs.

Rollback-only acceptance suite passed valid insert, fail-closed defaults, invalid slug/currency format/branch code, missing restaurant FK and duplicate branch code. The complete candidate transaction was rolled back. Post-rollback catalog verification: no Batch 2 tables, no Realtime entries, only Batch 1 migration history. All three Supabase advisors returned zero lints. Candidate is **not** approved/applied; separate explicit approval is required.

### 4.6 Initial tenant provisioning

- No restaurant or branch rows are seeded by a schema migration.
- A separate idempotent, audited provisioning command creates the initial Flame Chick restaurant and its branches.
- The initial tenant uses the agreed defaults `PKR` and `Asia/Karachi`, unless owner-approved settings differ before provisioning.
- Website capability flags remain false until explicitly enabled by Admin/Owner through an audited command.
- No default delivery fee, free delivery, default Not Listed fee or zero-fee fallback is inserted.
- Physical deletion is not an operational action; use `is_active = false` and preserve history.
- Do not add branch-specific base product prices in V1. Base catalogue/prices are restaurant-wide; branch-specific sellability overlays and delivery pricing are separate later batches.

- `phone text NULL` (normalized; private)
- `is_active boolean NOT NULL DEFAULT true`
- `created_at timestamptz NOT NULL DEFAULT transaction_timestamp()`
- `updated_at timestamptz NOT NULL DEFAULT transaction_timestamp()`

No public profile directory. Auth email remains in Supabase Auth unless a verified operational need requires a snapshot. A user cannot change role/branch through their profile.

### 5.2 public.user_roles

One role identity per user per restaurant, with optional same-role branch assignments for operational roles.

Columns:
- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `restaurant_id uuid NOT NULL REFERENCES restaurants(id) ON DELETE RESTRICT`
- `user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT`
- `role_key text NOT NULL CHECK IN ('admin','owner','manager','cashier','rider')`
- `branch_id uuid NULL`
- `is_active boolean NOT NULL DEFAULT true`
- `assigned_by uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT`
- `reason text NOT NULL` (bounded non-empty reason for role/branch grant)
- `created_at timestamptz NOT NULL DEFAULT transaction_timestamp()`
- `disabled_at timestamptz NULL`
- CHECK (`(is_active AND disabled_at IS NULL) OR (NOT is_active AND disabled_at IS NOT NULL)`).

Scope CHECK:
- admin/owner → branch_id IS NULL.
- manager/cashier/rider → branch_id IS NOT NULL.
- Composite FK (`branch_id, restaurant_id`) → branches(`id, restaurant_id`); because branch_id is nullable for Admin/Owner, MATCH SIMPLE is intentional.

Indexes/constraints:
- UNIQUE active restaurant-wide role per user: partial unique (`restaurant_id,user_id`) WHERE is_active AND branch_id IS NULL.
- UNIQUE active branch assignment per user/branch: partial unique (`restaurant_id,user_id,branch_id`) WHERE is_active AND branch_id IS NOT NULL.
- Index active roles for auth lookup: (`user_id,restaurant_id`) WHERE is_active.
- Index branch role operations: (`restaurant_id,branch_id,role_key`) WHERE is_active.
- A partial unique index cannot enforce the cross-row same-role rule. The staff command must lock the (restaurant_id,user_id) scope, read all active assignments, enforce exactly one role_key across all rows, and serialize the transition. Add a database-side constraint trigger/guard as defense in depth.
- Admin/Owner cannot coexist with operational branch rows; same-role operational rows may span multiple branches.
- Role changes disable old rows, insert new rows and append audit in one transaction.
- Never delete a role row to revoke access.

### 5.3 Last active Owner safeguard

- Role change/deactivation command obtains a transaction-scoped lock for the restaurant authority scope before checking the active Owner count.
- It must prevent removing/demoting/deactivating the final active Owner.
- Lock is held until transaction commits; do not rely on a non-locking COUNT query.
- Test concurrent Admin attempts to demote/deactivate different final Owner candidates.
- Admin and Owner may manage staff, but cannot remove the last active Owner.

### 5.4 public.staff_role_audit

Append-only event table:
- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `restaurant_id uuid NOT NULL`
- `branch_id uuid NULL`
- `target_user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT`
- `old_role_key text NULL`
- `new_role_key text NULL`
- `action text NOT NULL CHECK IN ('invited','activated','deactivated','role_changed','branch_changed')`
- `actor_user_id uuid NOT NULL`
- `actor_role_key text NOT NULL CHECK IN ('admin','owner')`
- `reason text NOT NULL`
- `request_id uuid NOT NULL`
- `occurred_at timestamptz NOT NULL DEFAULT clock_timestamp()`

No UPDATE/DELETE. Unique request_id/action scope prevents duplicate audit events for retries. Do not store invitation tokens or secrets. Composite tenant/branch relation applies when branch_id is non-null.

### 5.5 Invitation workflow state (private normalized tables)

Supabase Auth invite and PostgreSQL role assignment are not one ACID transaction. Use an idempotent recoverable state machine; keep invite PII and workflow state in `app_private`.

`app_private.staff_invitation_requests`:
- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `restaurant_id uuid NOT NULL REFERENCES public.restaurants(id) ON DELETE RESTRICT`
- `UNIQUE(id, restaurant_id)` (composite parent key for branch-target rows)
- `requested_by uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT`
- `normalized_email text NOT NULL` (private; normalize before insert)
- `role_key text NOT NULL CHECK IN ('admin','owner','manager','cashier','rider')`
- `status text NOT NULL CHECK IN ('pending','sent','accepted','failed','expired','cancelled')`
- `request_id uuid NOT NULL UNIQUE`
- `auth_user_id uuid NULL REFERENCES auth.users(id) ON DELETE RESTRICT`
- `failure_code text NULL` (safe stable code only; no raw Auth response/token)
- `created_at, updated_at timestamptz NOT NULL`

`app_private.staff_invitation_branch_targets`:
- `invitation_id uuid NOT NULL REFERENCES app_private.staff_invitation_requests(id) ON DELETE RESTRICT`
- `restaurant_id uuid NOT NULL`
- `branch_id uuid NOT NULL`
- PRIMARY KEY (`invitation_id, branch_id`)
- Composite FK (`branch_id, restaurant_id`) → `public.branches(id, restaurant_id)`
- Composite FK (`invitation_id, restaurant_id`) → `app_private.staff_invitation_requests(id, restaurant_id)` (add matching UNIQUE parent key).

Rules:
- Manager/Cashier/Rider invitations require one or more valid branch-target rows, all same restaurant and same role.
- Admin/Owner invitations are restaurant-wide and have no branch-target rows.
- Do not store invitation tokens or raw provider responses.
- Verify invited identity before binding/activating role. Reconcile Auth success + DB failure by retrying same request, not duplicating user/invite.
- Auth invite delivery and database role assignment remain a recoverable saga, not a single ACID transaction.

### 5.6 Staff permissions and RLS bootstrap

- No anonymous role-table access.
- Authenticated user may read only their minimal active role/profile projection where required for session bootstrap.
- No direct browser INSERT/UPDATE/DELETE on user_roles, staff audit or invitation state.
- Admin/Owner staff management via server command; verified actor and target branch/user checks inside transaction.
- Manager/Cashier/Rider cannot manage roles.
- RLS must be enabled on every exposed staff table and policy tested against actual branch context.
- Do not rely solely on the user_roles RLS policy to validate role changes; commands must enforce no self-escalation and last-Owner invariants.
